# 部署与回滚演练（M7）

> 本文件是 **M7 的可执行清单**。截至「M7 准备」阶段，工程侧已经做好不需要账号就能做的部分
> （可移植 CI、跨平台 Chrome 定位、严格 CSP、部署冒烟脚本）；真正部署需要你先提供素材/账号。
> 所有「人工确认」项都必须由真人签字，脚本不会冒充已经验证。

## 0. 本文件与规划书的关系

- `docs/项目设计与实现规划书.md` 的 M7 WBS（第 426–431 行）定义 DoD：
  ① 自定义域名 HTTPS 可访问；② 断网/禁用 JS 时正文仍可读；
  ③ 一次「发布→回滚→再发布」演练成功；④ 国内访问 Giscus/Cal.com/邮件送达/微信号兜底实测记录。
- 本文件把 ①②③ 拆成可执行步骤，并标注哪些已由脚本覆盖、哪些必须人工。
- 工程不变量（读路径全静态）意味着：**回滚 = 重新指向上一份静态产物**，不需要回滚数据库或会话。

## 2. 部署前：不依赖账号就能跑完的检查

```bash
pnpm install --frozen-lockfile
pnpm run quality           # build → test:csp → check/test:rules/test:unit → verify:ci
pnpm run quality:browser   # perf/search/lead/nodynamic/Playwright → Lighthouse → axe
pnpm deploy:smoke          # 本地托管 dist/，以消费端视角验 11 页 + feed + sitemap + Pagefind + 真 CSP 头
```

`pnpm deploy:smoke` 当前实测（2026-11-12）：`@@SMOKE@@ verdict:PASS / failed:0 / mode:local`，
11 个核心页 200、单一 h1、canonical 齐备；RSS 2.0 / JSON Feed 1.1 / sitemap / Pagefind UI
可消费；首页零可执行脚本；`script-src` 严格；图片带 `srcset`；联系/订阅/隐私页可达。

若 `astro.config.mjs` 的 `site` 仍是占位 `https://atelier.example.com`，**先换成真实域名**
（一处驱动 canonical / sitemap / OG / RSS / JSON Feed），再跑上面三条；换完需重跑
`pnpm test:csp`（`public/_headers` 哈希不变，但 `data-domains` 随 `site` 变化）。

## 3. 首次部署（Cloudflare Pages 为例）

1. 绑定 GitHub 仓库，构建命令 `pnpm build`，输出目录 `dist`，Node 版本 `24`，
   包管理器 `pnpm@11.28.5`（`packageManager` 字段已锁）。
2. 在平台「环境变量」里设置（**只放公开值；密钥绝不入库**）：
   - `PUBLIC_SITE_URL` = 真实域名
   - `PUBLIC_CONTACT_EMAIL`、`PUBLIC_CAL_URL`（可选，留空则分别降级 mailto / 不渲染预约入口）
   - `PUBLIC_FORM_ENDPOINT`（第三方表单端点；留空则表单整块降级为邮件链接）
   - `PUBLIC_UMAMI_SCRIPT_URL` + `PUBLIC_UMAMI_WEBSITE_ID`（必须同时配置，否则首屏保持零客户端 JS）
   - `RESEND_API_KEY` 仅在启用方案 B（R1.5 自建 Serverless）时需要，R1 方案 A 不用
3. 平台会读取 `public/_headers`，把 CSP 作为响应头发出。部署后**立即**跑远端冒烟：

   ```bash
   pnpm deploy:smoke:remote https://真实域名
   # 或 DEPLOY_URL=https://真实域名 pnpm deploy:smoke
   ```

   远端模式硬断言 11 页 / feed / sitemap / Pagefind / srcset；CSP 响应头只记录不判失败
   （不同平台对 `_headers` 的映射方式不同），按下表人工核对。

4. 自定义域名：在平台绑定域名 → 按提示改 DNS（A / CNAME）→ 等 HTTPS 证书签发 →
   浏览器打开 `https://域名/` 与 `https://域名/rss.xml` 确认无证书/重定向问题。

## 4. 发布 → 回滚 → 再发布演练（DoD ③）

演练目的不是「相信平台有回滚按钮」，而是**真的回滚一次并验证读路径不受影响**。

1. **记录基线**：记下当前部署的 commit SHA、部署 ID、时间；跑一次远端冒烟留档。
2. **制造一次可见变更**：用 `pnpm new:log "回滚演练"` 加一条 `build-log`（或改一处文案），
   `git push` → 等 CI 全绿 → 等平台部署完成 → 跑远端冒烟，确认新内容已在线上。
3. **回滚**：在平台部署历史里选上一份部署，点 Rollback / Redeploy → 等完成 →
   再跑 `pnpm deploy:smoke:remote https://真实域名`，确认：
   - 11 个核心页仍 200、单一 h1、正文可读；
   - RSS / JSON Feed / sitemap / Pagefind 仍可消费；
   - 首页零可执行脚本、图片仍带 srcset；
   - 刚才那条演练日志**不再出现**（证明确实回到了旧产物）。
4. **再发布**：把 HEAD 重新部署（或再 push 一条空提交触发），跑远端冒烟，确认演练日志回来。
5. **签字**：在本文件第 7 节表格填三次冒烟的时间、SHA、verdict 与操作人。未完成不勾 DoD ③。

> 因为「读路径全静态、动态层全部宕机也不影响读」，回滚期间表单/预约/分析可能短暂不可用，
> 但首页/作品/日志必须始终完整——这正是 M5 `test:nodynamic` 已经实测过的不变量。

## 5. 断网 / 禁用 JS 检查（DoD ②）

- 浏览器开 DevTools → Network 勾 Offline，或直接禁用 JavaScript 后刷新：
  首页、作品详情、日志详情、`/about` 的正文与导航仍应完整可读（纯 HTML + 一个 CSS 外链）。
- `/search` 是**唯一**依赖 JS 的页面（Pagefind 懒加载），断网/禁 JS 时它应显示降级说明，
  不影响其余页面——这是设计取舍，不是缺陷。
- 记录：浏览器、是否禁 JS、检查的 5 个 URL、结论。

## 8. 诚实边界

- `deploy-smoke` **不**验证：表单外部送达、DNS 邮件记录、国内可访问性、Lighthouse 分数、axe。
  这些分别由第 6 节人工表 / `quality:browser` / 真人浏览器负责。
- CI（`.github/workflows/ci.yml`）目前是 `ubuntu-latest` 标准写法，但**尚未在 GitHub 托管
  runner 上实跑过**；首次 push 到远端仓库是 M7 的一个独立验收点，不假称已通过。
- 部署 job 刻意未写进 `ci.yml`：平台账号与域名到位前，把部署塞进 CI 只会制造假绿。
