# 能力提炼指南

> **定位**：把日常开发中做过的事，变成可信、可验证、可挂证据的"能力条目"的操作手册。
> 本指南是 [命令手册.md](命令手册.md) §3.3 `new:capability` 的**方法论前置**——命令只生成骨架，判断力在这里。
> 概念源头：[产品分析与概要设计.md](产品分析与概要设计.md)（"证据优先于形容词"，见 :29 / :167 / :182）；
> 数据约束：[`src/content.config.ts`](../src/content.config.ts) 的 capabilities 集合（E4，见 :84-102）。

---

## 0. 先记住一句话

**能力不是"我会什么"，是"我用什么做成了什么、结果如何、证据在哪"。**

本项目对"能力"的定义是硬性的：`capability → evidence(product / log / case)`，禁止无证据的形容词。
一条能力 = 一句 `statement` + 2~3 条可点击的证据 + 可验证的结果。没有证据的能力不允许发布（E4 会让 build 失败）。

因此提炼能力之前，先问自己三个问题：
1. 我有没有**反复、成体系**地做到过这件事（不是一次巧合）？
2. 我能不能拿出 ≥2 条**真实可点开**的证据？
3. 半年后这条描述还成立吗？

三个都是"是"，才值得落一条。

## 1. 常见 / 应具备的能力维度（候选清单）

`category` 在 schema 里是自由字符串（`src/content.config.ts:89`），现有两条用了"工程""产品"。
下面按独立开发者实际场景归为 5 类，列出**候选能力**——只有当它有证据支撑时才落地，不要照单全收。

### 1.1 工程
- 全栈交付（从概念 → 数据模型 → 上线可维护）✅ 已有 `full-stack-delivery`
- 架构与技术选型（把读/写路径拆开、静态优先）
- 质量门禁与自动化测试（把"跑过一次"固化成可复现命令）
- 性能工程（预算制：LCP/CLS/首屏 JS 上限）
- 安全设计（CSP、密钥隔离、非对称签名）
- 可移植 CI/CD（任何机器上都能跑的门禁）

### 1.2 产品
- 产品分析与技术选型（竞品核验、方案裁剪、版本基线）✅ 已有 `product-analysis`
- 需求抽象（模糊需求 → 产品概念 → 可排期方案）
- 数据模型设计（结构化内容、证据链模型）
- 转化闭环设计（触达 → 理解 → 证据 → 线索 → 客户 → 口碑）

### 1.3 设计
- 信息架构与分层取舍（首屏预算、内容分层、复杂度分档）
- 无障碍（a11y：axe 0 违规）
- 内容分层组织（把碎片整理成体系）

### 1.4 交付与运维
- 部署与回滚演练（发布 → 回滚 → 再发布闭环）
- 消费端冒烟验证（"按钮绿 ≠ 上线"，用事实验真）
- 零密钥 / 零停机发布
- 工具化写作流（把重复操作变成一条命令）

### 1.5 协作与元能力
- 文档驱动开发（docs/ 作为设计与决策的单一来源）
- 决策记录与复盘（把"为什么"和"放弃了什么"写下来）
- Build in Public（把过程变成结构化证据的能力）

## 2. 开发中应该注意什么

1. **边做边留证据，别等事后补**。能力的原料是日志和作品。关键时刻写一条 `decision`（为什么这么选、放弃了什么）或 `retro`（哪里踩坑、怎么收口），原料就这么攒出来的。当时没记，事后编不出来。
2. **记"为什么"和"放弃了什么"，不只记"做了什么"**。流水账没有证明力，决策过程才有。
3. **要数字，不要形容词**。"LCP<1.5s、Lighthouse 100、首屏 JS≤50KB"远胜"性能很好"；"零 API Token 完成回滚"远胜"熟悉部署"。
4. **每条证据必须真实可点开**。这条已由 E4 硬校验强制（`evidence_ids` 指向不存在的条目会让 build 失败，`src/content.config.ts:91-100`）。
5. **粒度要大、要稳定**。别给每个小任务建一条；能力是"可复用的证明模式"，半年后仍成立才算。
6. **能力是事后抽象的**。新建作品时，支撑它的日志还没写——自动生成只会得到空话 + 悬空证据。所以：**先做事 → 留证据 → 再回头沉淀**。这也是为什么工具是半自动的 `new:capability`，而不是在 `new:product` 时自动生成。

## 3. 怎么提炼：五步法

**触发信号**（满足任一就考虑提炼）：
- 同类问题解决了 ≥2 次；
- 有人问"你擅长 X 吗"，你能举出多个不同场景的例子；
- 某个决策沉淀出了一套**可复用的方法 / 取舍原则**。

**步骤**：

1. **翻日志与作品**：找出反复出现的行为模式（跨多条的共性，而非单篇）。
2. **写一句 statement**：公式 = `动词 + 对象 + 可验证结果`。
   例："能把一个产品从概念设计落到可访问、可维护、可演进的线上系统"（现有 `full-stack-delivery` 的写法）。
3. **挑 2~3 条最强证据**：跨来源组合（作品 + 决策日志 + 复盘），逐条点开确认能看到具体做法。
4. **生成骨架**：
   ```bash
   pnpm new:capability "能力名" --category=工程 --statement="..." \
     --evidence=products/xxx,log/yyy
   ```
   E4 会校验证据真实性（详见 [命令手册.md](命令手册.md) §3.3）。
5. **定期回访**：以后有了更强的新证据，回头更新 `evidence_ids`，让能力"长硬"。

## 4. 落地检查清单（提交前逐条过）

- [ ] `statement` 是"动词 + 对象 + 可验证结果"，不含"精通/熟练/熟悉"等形容词
- [ ] `category` 填写一个稳定的分类（工程 / 产品 / 设计 / 交付运维 / 元能力）
- [ ] `evidence_ids` ≥1 条（建议 2~3 条），格式为 `"<集合名>/<id>"`
- [ ] 每条证据目标**真实存在**且点开看得到具体做法（跑 `pnpm build` 让 E4 校验）
- [ ] 证据跨来源（不要全来自同一篇日志）
- [ ] `pnpm run quality` 全绿后，与内容同批 `git commit/push`

## 5. 用现有日志可直接提炼的示例（证据均已存在）

以下仅为示范，未落地为能力条目；真正发布前请按第 4 节清单自审。

**示例 A · 信息架构与分层取舍**（`category: 设计`）
- statement：能把复杂功能按隐私 / 复杂度边界分层，给出用户可按需选择的清晰结构
- 证据候选：`log/2026-11-21-四种整理方式的分层取舍`（焕名四档分层）+ `log/2026-11-12-first-screen-budget`（首屏硬性预算）

**示例 B · 安全与许可体系设计**（`category: 工程`）
- statement：能在产品上线前把安全机制从可绕过方案升级为可验证方案，并守住密钥边界
- 证据候选：`log/2026-11-21-给激活码做非对称签名`（Ed25519、客户端只留公钥、两个静默降级坑）+ 相关作品

**示例 C · 交付验真与可回滚发布**（`category: 交付运维`）
- statement：能把"部署成功"从平台按钮的绿，变成消费端可验证、可回滚闭环的事实
- 证据候选：`log/2026-11-13-绿灯不等于上线`（CF 报成功却发布源码，冒烟暴露）+ `log/2026-11-13-第一次上线与回滚演练`（哨兵验证回滚生效）

> 提炼示例的能力时，记得 `pnpm new:capability` 只保证骨架合规，`statement` 与证据选择仍需人工判断——这是工具故意留给人类的部分。
