## 现象：源码能跑，打包版崩

开发时「本地模型」页一切正常，一到 Nuitka 打出来的单文件 EXE 里就报 `No module named 'api'`。这类 bug 最烦的地方在于：源码测试全绿，只有用户拿到的那份产物是坏的。

## 根因：同一份代码，两个模块名

有 4 处惰性导入在源码树里写成顶层 `from api import client`——源码运行时 `api` 在路径上，能找到；Nuitka 把源码编成包后，模块名变成 `src.api`，`api` 反而找不到了。是打包前后模块命名空间不一致，不是依赖漏装。

## 修法：兼容两种运行形态

把 4 处统一改成先相对导入、失败再退回顶层：

```python
try:
    from ..api import client
except ImportError:
    from api import client
```

这样源码形态和打包形态都能加载同一份逻辑。但只改导入还不够——下次谁再加一个顶层 `from api import ...`，同样的坑会再踩一遍。于是补了一条 `test_pack_manifest` 护栏，把「打包清单里不能有会踩命名空间差异的导入方式」固化成测试，让回归在 CI 阶段就红，而不是等用户反馈。

## 顺手做掉的两件事

同一轮还处理了：

- **单文件 EXE 图标**：`app_icon_path()` 上溯两级定位 `main.ico`，用 `--include-data-files` 显式打进包里，否则 Nuitka 单文件模式下图标资源不在预期路径。
- **keygen 也单文件化**：授权码生成器打成 34.8 MB 的单文件 EXE，和主程序分发形态一致。

## 下次怎么避免

打包相关的问题有个共同特征：**开发期不可见，只有产物能暴露**。所以「npm/pytest 全绿」不能作为交付标准，必须把产物本身纳入验证——冷启动跑一次、每个页签点一遍、离线场景断网试一次。这条已经写进发布前清单，和「绿灯不等于上线」是同一类教训在不同项目里的复现。
