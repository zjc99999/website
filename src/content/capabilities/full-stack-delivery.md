## 主张：不写「精通全栈」，用一条跑通的链路说话

「精通全栈」是简历上最廉价的一句话。全栈交付能力不是会多少框架，而是能不能一个人把产品从概念设计推到可访问、可维护、可演进的线上系统，并且每一步的决定都有据可查。判断标准还是那个：链路真的跑通了吗？

## 从概念到脚手架，一天内立起来

Atelier 这个站本身就是证据。最小工程一天内立起来：`pnpm install` 295 个包、零 peer 冲突；`pnpm build` 以 `output: "static"` 产出 `dist/index.html` 1554 B、零客户端 JS；`pnpm check` 0 errors / 0 warnings / 0 hints；`--frozen-lockfile` 可复现。

过程中记录了两个真实的坑，说明验证不是走过场：Astro 7 把 `compressHTML` 默认值从 `true` 改成 `'jsx'`，会吞掉行内元素之间的空格，中文文案行内链接多，显式设回 `true` 才稳；TypeScript latest 已到 7.0.2，但 `@astrojs/check` 的 peer 只接受 `^5 || ^6`，所以锁死 6.0.3 不跟 latest。**把版本冲突和默认值变化记下来**，就是可维护性的开始。

## 架构决定：把读路径和写路径拆开

最关键的一个决定是把系统切成两半：**读路径全静态**（Git 里的 MDX → 构建成 HTML → CDN），**写路径才动态**（订阅、联系表单）。收益很直接：

- 没有数据库、没有会话、没有运行时依赖，部署就是传一堆 HTML；
- 第三方表单、邮件、分析服务即使全挂，访客照样能看完整个网站；
- 内容与代码同仓，`git push` 就是发布，版本史就是备份。

代价是「在线后台编辑」要等真有第二个人写内容时再做——独立开发者最怕的不是功能少，是运维把自己拖垮，这个代价现在完全付得起。全栈能力不是把所有层都堆上，而是**知道哪一层可以不要**。

## 可演进：把组织化字段提前埋好

可演进性体现在早期决定里：`workspace_id` / `owner_member_id` 从第一条内容就存在，将来组团队不用改语义；内容模型把作品、日志、能力、案例、页面分开，能力必须挂真实证据（构建期校验，坏 id 直接让 build 失败）。这些决定让站点今天一个人写、明天多人协作都能平滑演进。

每一步的决策理由都写在日志里——从概要设计、数据模型、技术选型到脚手架与构建验证，一个人一条链跑下来。看下面三条证据，就能核对这条链路。
