## 主张：分析要落到可执行的结论，而不是一份漂亮的 PPT

「产品分析」如果只是列一堆竞品名字和功能对比表，价值有限。真正的分析能力，是把模糊需求收敛成产品概念、把市场事实核验清楚、最后落到一份能排期、能验证的技术方案。判断标准很简单：看完分析，能不能直接开工？

## 把形容词变成能验收的数字

以 Atelier 的首屏设计为例。「简洁、一目了然」是形容词，不能指导开发。分析阶段把它拆成硬约束：首屏（不滚动）只允许身份一句话、价值主张一句话、最多 3 张作品卡、1 个主 CTA、1 个次 CTA、导航不超过 5 项；禁止长段落、技能标签云、全量日志列表、动效轮播、第三方聊天挂件、cookie 横幅。

再配性能预算：首屏 JS ≤50KB、LCP <1.5s、CLS <0.1、Lighthouse ≥95。验收方式也不是「我觉得挺简洁」，而是找 5 个人做「3 秒测试」——看 3 秒后能不能说清我是谁、做什么、能帮他什么、下一步点哪，至少 4 个人说得出才算过。**把主观审美变成可测量的验收条件**，这是分析落到执行的关键一步。

## 事实要核验，不靠印象

技术选型里最容易出错的是版本号和许可证。Atelier 的概要设计与规划书把概念、竞品、数据模型、排期、约束、差异登记都写进仓库（`docs/产品分析与概要设计.md`、`docs/项目设计与实现规划书.md`），所有版本号和许可证都经 registry / GitHub API 核验过，不是凭记忆写。

这块纪律在别的项目里是同一套做法：竞品要列出可对标的真实产品，许可要逐条核到条款正文，依赖要把「不可核验」的数量压到 0 再下结论。**结论背后有可追溯的事实来源**，而不是「大家都这么说」。

## 方案裁剪：先做读路径，复杂等需要时再加

分析还要决定「先不做什么」。Atelier 最关键的一个决定是把系统切成两半：读路径全静态（Git 里的 MDX → 构建成 HTML → CDN），写路径才动态（订阅、联系表单）。这样没有数据库、没有会话、没有运行时依赖，部署就是传一堆 HTML；第三方服务全挂，访客照样能看完网站。代价是「在线后台编辑」要等真有第二个人写内容时再做——这个代价现在付得起。
